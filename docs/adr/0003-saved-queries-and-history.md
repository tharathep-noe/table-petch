# Saved queries and query history: two stores, two scopes, capture in main

The app gains two ways to recall past SQL: a curated **saved-query** library and an
automatic **query history**. They look similar but are mechanically opposite — one
explicit and edited, one automatic and append-only — and the design treats them
differently on purpose. Each decision below was a real choice with a simpler
alternative we rejected.

1. **Two separate `userData` JSON files, fail-safe, IPC-only.** `savedQueries.json`
   and `queryHistory.json` follow the `store.ts` / `sessionStore.ts` pattern: the
   main process owns them, the renderer reaches them only through `TablePetchApi`,
   and a missing / unparseable / unknown-`version` file loads as empty. We kept them
   in _separate_ files rather than one combined app-state file because they have
   different write cadences (history appends on every run; saved queries change only
   on explicit user action) and different privacy profiles (history may hold literal
   values; the saved library is deliberate text).

2. **History is captured in the main `runQuery` handler, not by the renderer.**
   There is no `appendHistory` on the API. The `runQuery` IPC handler is the single
   chokepoint where the SQL, the `pg` command tag, and the wall-clock duration are
   all already in hand, so it builds the `HistoryEntry` and appends it as a contained
   side effect. We rejected a renderer-facing append (the obvious alternative)
   because it could be bypassed or double-fired, and it would force the renderer to
   re-derive the command tag and timing the main side already knows.

3. **History logs only user-authored editor runs — but the shape admits more.**
   Only statements run through `runQuery` are logged; the synthesized `UPDATE` /
   `INSERT` / `DELETE` behind a staged commit and the `SELECT`s generated by
   browsing a table are not. History is "what the user wrote," not an audit log. To
   avoid a future migration, every entry carries a `source: 'query' | 'commit'`
   discriminator — `'query'` is the only value emitted now; commit logging can be
   turned on later by writing `'commit'` entries.

4. **History is scoped per connection; the saved library is global.** Each history
   entry stores its `connectionId` and the view filters to the active connection —
   a `prod` query is noise on local, and history is privacy-sensitive. Saved queries
   carry only an _optional_ originating `connectionId` and are shown as one global
   list, because a curated snippet is often deliberately reusable across
   environments. We rejected uniform scoping (simpler to build and explain) because
   it fits neither concern's actual use.

5. **Reads collapse, writes don't.** Consecutive entries with identical SQL, against
   the same connection and database, fold into one **iff** the execution is a pure
   read (every `pg` command tag is `SELECT` / read) or a failure; any write is always
   recorded separately. The reasoning: re-running a `SELECT` while iterating is the
   common case and three identical rows are noise, but two `UPDATE`s are two real
   changes to the data and must each be visible. A failure collapses like a read —
   an aborted attempt changed nothing.

## Consequences

- `queryHistory.json` is capped at 500 entries, FIFO; the whole file is read and
  written at once, so the cap also keeps it small (same load-everything pattern as
  `session.json`).
- Both files fail safe to empty on a missing / unparseable / unrecognized-`version`
  file (forward-only; bump `version` with an explicit migration when a shape
  changes).
- Deleting a connection cascades to clearing that connection's history, so
  privacy-sensitive entries don't outlive the connection that produced them. Saved
  queries are unaffected (they're global).
- Management in this pass: per-connection "Clear history", a global "Clear all", and
  saved-query delete behind a confirm. Per-row history delete and a disable/pause
  toggle are deferred — both are one localized change away (the toggle is a single
  guard in the `runQuery` handler).
- Both surfaces open SQL into a fresh, un-run tab (consistent with the "never
  auto-run editor SQL" rule in [ADR 0002](./0002-session-persistence.md)); the user
  presses run.
